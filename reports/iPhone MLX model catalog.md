# Beacon Gains Better Models Without Bloat
**Beacon should add `mlx-community/MiniCPM5-2B-mlx-4Bit` and `mlx-community/Qwen3-4B-Instruct-2507-4bit`, while correcting six existing records and one additional rounding error.** MiniCPM5 is the strongest immediate quality-per-byte addition at **1.43 decimal GB and 2.52B parameters**; Qwen3 4B creates a useful premium text tier at **2.28 GB and 4.02B parameters**. Both expose model types registered by Beacon's pinned `mlx-swift-lm` 3.31.3 runtime, are ungated, include chat templates, and use Apache-2.0 licensing, so neither requires a repository-specific runtime preset. Phi-4 Mini is a promising same-size successor to Phi-3.5, but it should replace rather than duplicate the incumbent after an A/B device test. The strongest missing vision models are also statically supported, but license review, processor-path testing, image-memory measurement, or specialist UX work keeps them out of the add-now tier. Beacon should preserve every current model for now; the evidence supports metadata repair and tested replacement, not immediate deletion.

## Two text models add distinct capability tiers
Beacon's existing catalog is dense below 2 GB: it already has three general text choices around 0.66-0.98 GB and two 3B choices around 1.75 GB. Adding older compact checkpoints would increase choice without increasing capability. MiniCPM5 is different. Its current snapshot totals **1,426,011,807 bytes**, and its safetensors inventory contains **2,516,756,480 parameters**. OpenBMB positions the final post-trained checkpoint for coding, mathematics, long context, tool use, and agentic tasks, and reports a 53.9 aggregate score against 33.2 for LFM2.5 2.6B and 42.7 for Granite 4.2 3B. Those are vendor results rather than independent iPhone measurements, but they establish a credible new quality-per-byte point rather than another interchangeable small chat model. The upstream checkpoint deliberately uses a conventional Llama configuration and targets resource-constrained deployment, reducing integration risk relative to a novel architecture ([MiniCPM5 model card](https://huggingface.co/openbmb/MiniCPM5-2B); [MLX repository API](https://huggingface.co/api/models/mlx-community/MiniCPM5-2B-mlx-4Bit?blobs=true)).

Qwen3 4B Instruct 2507 fills a different gap: a single premium general model between the crowded sub-2-GB tier and the practical iPhone ceiling. Its snapshot is **2,278,972,236 bytes** with **4,022,468,096 parameters**. Qwen describes this 2507 release as non-thinking-only and reports major improvements over the original Qwen3 4B non-thinking mode, including MMLU-Pro 69.6 versus 58.0 and Arena-Hard v2 43.4 versus 9.5. It should therefore be cataloged as `regular`, not `reasoning`, despite strong reasoning benchmarks ([Qwen3 4B Instruct 2507 model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507); [MLX repository API](https://huggingface.co/api/models/mlx-community/Qwen3-4B-Instruct-2507-4bit?blobs=true)). Its larger working set warrants an opt-in placement, moderate default context, and the same `iPhone 15 Pro+` recommendation Beacon already applies to similarly large models. The advertised 256K context is not an iPhone operating target; Qwen itself recommends reducing context to 32,768 when memory is constrained ([Qwen3 4B Instruct 2507 model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)).

Phi-4 Mini does not justify a parallel slot. Its **2.18 GB**, **3.84B-parameter** conversion occupies almost exactly Phi-3.5 Mini's existing niche, while Microsoft's same-platform table shows a mixed but generally improved successor: Phi-4 leads the overall score 63.5 to 60.5 and makes large gains on BBH, GSM8K, and MATH, while Phi-3.5 still wins Arena-Hard, GPQA, HellaSwag, PIQA, and other tasks. Beacon should A/B test the exact conversion and replace Phi-3.5 only if its own prompts and device metrics confirm the upgrade ([Microsoft Phi-4 Mini model card](https://huggingface.co/microsoft/Phi-4-mini-instruct); [MLX repository API](https://huggingface.co/api/models/mlx-community/Phi-4-mini-instruct-4bit?blobs=true)).

## Runtime 3.31.3 supports every shortlisted architecture
Beacon resolves `mlx-swift-lm` **3.31.3 at commit `1c05248bb0899e2a7a4962b84d319cf12f4e12aa`** ([Beacon package resolution](../beacon.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved); [3.31.3 release](https://github.com/ml-explore/mlx-swift-lm/releases/tag/3.31.3)). At that exact revision, the LLM factory registers MiniCPM5's `llama`, Qwen's `qwen3`, and Phi-4 Mini's `phi3`. It decodes `config.json`, selects the creator by `model_type`, loads weights and tokenizer assets, and applies the tokenizer chat template. Beacon's default `ModelConfiguration(id:)` path is therefore statically sufficient; membership in the runtime's advertised `all()` list is not required ([pinned LLM factory](https://github.com/ml-explore/mlx-swift-lm/blob/1c05248bb0899e2a7a4962b84d319cf12f4e12aa/Libraries/MLXLLM/LLMModelFactory.swift); [generic registry fallback](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXLMCommon/Registries/AbstractModelRegistry.swift#L31-L45)).

The vision shortlist also clears static registration. Version 3.31.3 maps `lfm2_vl`, `llava_qwen2`, `mistral3`, and `glm_ocr` to native VLM implementations and registers `Lfm2VlProcessor`, `FastVLMProcessor`, `Mistral3Processor`, and `Glm46VProcessor`. Two details matter in testing: the runtime overrides Ministral's declared Pixtral processor with `Mistral3Processor`, and GLM-OCR works because the loader prefers its `preprocessor_config.json`, which names the registered `Glm46VProcessor` ([pinned VLM factory](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXVLM/VLMModelFactory.swift)). These mappings prove that the factory recognizes each configuration; they do not prove that image preprocessing, tensor naming, first-token generation, follow-up turns, or peak memory are stable on a physical iPhone.

The admission gate should therefore remain operational rather than architectural. Before publication, each exact repository should pass cold load, first-token generation, sustained generation, long-chat memory, cancellation/reload, and thermal tests on the oldest recommended device. Vision models additionally need maximum-resolution image preprocessing and follow-up-turn tests. Apple's Metal API describes `recommendedMaxWorkingSetSize` as the approximate allocation that avoids harming performance, and the pinned runtime itself budgets weights together with workspace and KV cache rather than equating download size with memory use ([Apple Metal guidance](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize); [pinned wired-memory policy](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXLMCommon/WiredMemoryPolicies.swift#L116-L170)).

## Vision candidates need tests or product decisions
`mlx-community/LFM2.5-VL-1.6B-4bit` is the best balanced deferred VLM. It totals **1.50 GB** and **1.60B tensor parameters**, combining a 1.2B language backbone with a 400M vision encoder. Liquid describes high-resolution tiling, native-resolution input, OCR and document use, multi-image input, and eight supported languages; its published table improves over LFM2-VL across most listed visual benchmarks ([LFM2.5-VL model card](https://huggingface.co/LiquidAI/LFM2.5-VL-1.6B); [MLX repository API](https://huggingface.co/api/models/mlx-community/LFM2.5-VL-1.6B-4bit?blobs=true)). It should undergo a direct comparison with Qwen2-VL rather than trigger an immediate removal. Its non-SPDX Liquid LFM 1.0 license also needs product/legal review before release ([LFM license](https://huggingface.co/LiquidAI/LFM2.5-VL-1.6B/blob/main/LICENSE)).

FastVLM and Ministral serve useful but narrower tiers. Apple's **1.27 GB**, **0.62B-parameter** BF16 FastVLM claims an 85-fold faster visual time to first token and a 3.4-fold smaller vision encoder than LLaVA-OneVision-0.5B, making latency its reason to coexist with SmolVLM2; however, it is not a smaller download and carries the Apple ML Research license ([FastVLM model card](https://huggingface.co/apple/FastVLM-0.5B); [MLX repository API](https://huggingface.co/api/models/mlx-community/FastVLM-0.5B-bf16?blobs=true)). Ministral is the clearest premium VLM at **2.78 GB and 3.85B parameters**, but vision activations, BF16 components, and KV cache leave little iPhone headroom beyond the snapshot. It belongs on the newest Pro-class devices only after explicit memory and thermal validation ([Ministral repository API](https://huggingface.co/api/models/mlx-community/Ministral-3-3B-Instruct-2512-4bit?blobs=true); [Ministral model card](https://huggingface.co/mistralai/Ministral-3-3B-Instruct-2512)).

GLM-OCR is not a general visual-chat model. Its **1.25 GB** conversion is compact and MIT-licensed, but the official card restricts prompts to text, formula, and table recognition or strict-schema extraction. It belongs in Beacon only after the product can label and route a dedicated document/OCR role; presenting it beside general image assistants would overpromise ([GLM-OCR model card](https://huggingface.co/zai-org/GLM-OCR); [MLX repository API](https://huggingface.co/api/models/mlx-community/GLM-OCR-4bit?blobs=true)).

## Seven catalog records require immediate repair
Beacon currently mixes repository storage with current-snapshot download size. `usedStorage` can include superseded LFS objects, while a reproducible catalog download estimate is the sum of current `siblings[].size` values divided by 1,000,000,000. That error nearly doubles Qwen3 0.6B, Llama 3.2 1B, and DeepSeek R1 Distill: their corrected values are **0.35 GB, 0.71 GB, and 1.01 GB**, respectively. Qwen2-VL should be **1.26 GB**, and Qwen2.5 Coder's 1.748 GB snapshot rounds conventionally to **1.75 GB**, not 1.74 ([Hugging Face Hub API documentation](https://huggingface.co/docs/hub/api); [Qwen3 API](https://huggingface.co/api/models/mlx-community/Qwen3-0.6B-4bit?blobs=true); [Llama API](https://huggingface.co/api/models/mlx-community/Llama-3.2-1B-Instruct-4bit?blobs=true); [DeepSeek API](https://huggingface.co/api/models/mlx-community/DeepSeek-R1-Distill-Qwen-1.5B-4bit?blobs=true); [Qwen2-VL API](https://huggingface.co/api/models/mlx-community/Qwen2-VL-2B-Instruct-4bit?blobs=true); [Qwen Coder API](https://huggingface.co/api/models/mlx-community/Qwen2.5-Coder-3B-Instruct-4bit?blobs=true)).

If `updatedAt` means Hugging Face `lastModified`, LFM2 must change from September 17, 2026 to **July 11, 2025**, and Qwen2-VL must change to **March 24, 2025**. Beacon should document that definition; otherwise the field ambiguously mixes repository updates with catalog review dates ([LFM2 API](https://huggingface.co/api/models/mlx-community/LFM2-1.2B-4bit); [Qwen2-VL API](https://huggingface.co/api/models/mlx-community/Qwen2-VL-2B-Instruct-4bit)). SmolVLM2's canonical owner is now `mlx-community`, not `HuggingFaceTB`. That correction should ship with a runtime switch update because Beacon currently special-cases only the redirected old ID ([canonical SmolVLM2 API](https://huggingface.co/api/models/mlx-community/SmolVLM2-500M-Video-Instruct-mlx); [Beacon runtime](../beacon/Services/BeaconModelRuntime.swift#L478-L486)). All current `supportsImages` values are already correct, and no current repository is disabled or gated, so no other immediate removals or modality changes are supported by the audit.

## Conclusion
The practical catalog strategy is to spend slots on capability steps, not family breadth. MiniCPM5 creates a low-risk 2026 quality-per-byte option, and Qwen3 4B creates one clearly bounded premium text tier. The remaining shortlist is valuable precisely as a validation queue: Phi-4 can displace an incumbent, LFM2.5-VL can challenge the current balanced VLM, FastVLM can earn a latency role, Ministral can prove a high-end tier, and GLM-OCR can justify a specialist workflow.

Because Beacon downloads mutable `main` revisions, metadata correctness will decay again unless releases pin repository revisions or re-query the Hub before catalog publication. The catalog should treat decimal snapshot GB as download UX, device testing as the compatibility authority, and parameter count as a separate model-capacity field.
