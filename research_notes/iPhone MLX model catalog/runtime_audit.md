# Beacon iPhone MLX Model Catalog / Runtime Audit

Audit snapshot: September 29, 2026. Runtime: `mlx-swift-lm` tag `3.31.3`, commit `1c05248bb0899e2a7a4962b84d319cf12f4e12aa`. Catalog reviewed: [`beacon/Resources/models.json`](../../beacon/Resources/models.json).

## Which model types and processor architectures are supported by the pinned registries?

### Takeaway

Repository compatibility is determined by the exact `model_type` in `config.json`; a VLM additionally needs a recognized `processor_class` in `preprocessor_config.json` or `processor_config.json`. Presence in `LLMRegistry.all()` or `VLMRegistry.all()` is not required, because an unknown repository ID falls back to a plain `ModelConfiguration`, but a matching type and processor are required at model creation time.

### Cited Findings

- The audited checkout is tag `3.31.3`; its package requires iOS 17 and pins `mlx-swift` from `0.31.3`. The local tag/commit was verified directly, and the package constraints are visible upstream. - [Package.swift at 3.31.3](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Package.swift#L7-L14); [dependency declaration](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Package.swift#L38-L40)

### Inferences

- Admission should be mechanical: require an ungated, enabled repository; exact registry-compatible `model_type`; for vision, exact compatible `processor_class`; a chat template; identifiable license; and HEAD download bytes at or below 3.0 GB. Architecture names such as `Qwen2ForCausalLM` are descriptive but are not the factory lookup key. - [LLM load path](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXLLM/LLMModelFactory.swift#L501-L527); [VLM load path](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXVLM/VLMModelFactory.swift#L324-L348)
- For VLMs, checking only `model_type` is unsafe: a missing or renamed processor class will fail after the weights are selected. - [VLM processor loading](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXVLM/VLMModelFactory.swift#L369-L407)
- Pin the repository revision/SHA in a production catalog or revalidate metadata regularly. Beacon currently requests `main`, so a future config or processor change can break an otherwise unchanged catalog entry. - [Model configuration default revision](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXLMCommon/ModelConfiguration.swift#L105-L117); [Hugging Face API documentation](https://huggingface.co/docs/hub/api)

### Gaps

- Registry matching proves that configuration decoding is implemented, not that a particular conversion is numerically correct, thermally acceptable, or stable under iOS memory pressure. Those properties require device smoke tests.
- The runtime has overlapping keys in LLM and VLM registries, notably `gemma3`, `gemma4`, `mistral3`, `qwen3_5`, and `qwen3_5_moe`; candidate validation must therefore include modality and processor metadata rather than selecting a factory from `model_type` alone. - [LLM registry](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXLLM/LLMModelFactory.swift#L20-L79); [VLM registry](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXVLM/VLMModelFactory.swift#L80-L135)

## Which compact presets or popular models are absent?

### Takeaway

The strict shortlist is `mlx-community/MiniCPM5-2B-mlx-4Bit` as the best quality/byte addition and `mlx-community/Qwen3-4B-Instruct-2507-4bit` as the premium text tier. After device validation, replace Phi-3.5 with Phi-4 Mini and Qwen2-VL with LFM2.5-VL rather than retaining both generations; most older compact presets are redundant, too weak, or lack a robust chat setup.

### Inferences

- The catalog should add capability tiers, not model-family variety for its own sake. MiniCPM5 adds a new 2026 quality/byte point at 1.426 GB, while Qwen3 4B Instruct opens a materially larger premium text tier at 2.279 GB. - [MiniCPM5 API](https://huggingface.co/api/models/mlx-community/MiniCPM5-2B-mlx-4Bit?blobs=true); [Qwen3 Instruct API](https://huggingface.co/api/models/mlx-community/Qwen3-4B-Instruct-2507-4bit?blobs=true); [Beacon catalog](../../beacon/Resources/models.json)
- If the list must remain the same length, the first curation change should be removal or replacement of the older `LFM2-1.2B-4bit`, because LFM2.5 occupies the same 0.663 GB download slot with explicit Instruct naming and newer metadata. This is capability overlap, not an assertion that the weights are identical. - [LFM2 API](https://huggingface.co/api/models/mlx-community/LFM2-1.2B-4bit?blobs=true); [LFM2.5 API](https://huggingface.co/api/models/mlx-community/LFM2.5-1.2B-Instruct-4bit?blobs=true)
- Require a real instruction/chat signal: an explicit Instruct/Chat model name or authoritative card statement plus a usable chat template. A template alone is insufficient when the conversion identifies a base checkpoint. - [Qwen3.5 2B API](https://huggingface.co/api/models/mlx-community/Qwen3.5-2B-4bit?blobs=true)

### Gaps

- Popularity is not quality. No standardized Beacon prompt suite or on-device tokens/second, peak-memory, thermal, or task-quality results were available for ranking the candidates.
- MiniCPM5, Qwen3 4B Instruct, Phi-4 Mini, LFM2.5-VL, and FastVLM have strong static compatibility evidence, but none should ship before load/generation, long-chat memory, cancellation/reload, and target-device thermal tests; VLMs additionally require image preprocessing and follow-up-turn tests.

## Are current catalog metadata values clearly wrong?

### Takeaway

All 13 entries resolve and are runtime-compatible, ungated conversions; all current `supportsImages` flags are correct. Four download sizes, two dates, and one repository owner are clearly stale or wrong, and the catalog has avoidable capability duplication.

It does have curation overlap: LFM2 and LFM2.5 occupy the same size/family slot, and several Qwen/general 1-2B models target nearly identical use cases. - [Beacon catalog](../../beacon/Resources/models.json); [LFM2 API](https://huggingface.co/api/models/mlx-community/LFM2-1.2B-4bit); [LFM2.5 API](https://huggingface.co/api/models/mlx-community/LFM2.5-1.2B-Instruct-4bit)

### Inferences

- Define `sizeInGB` as the sum of files downloaded from the selected revision, divided by 1,000,000,000, and document that it is decimal GB. Do not source it from `usedStorage`, safetensor parameter count, or model-card prose. - [HF blobs response](https://huggingface.co/api/models/mlx-community/Qwen3-0.6B-4bit?blobs=true)
- Define `updatedAt` explicitly as Hugging Face `lastModified`, or rename it if Beacon intends it to mean """catalog entry reviewed.""" The current data mixes those concepts. - [Beacon catalog](../../beacon/Resources/models.json); [LFM2 API](https://huggingface.co/api/models/mlx-community/LFM2-1.2B-4bit)
- Changing SmolVLM2 to its canonical ID should be paired with a runtime review because Beacon's preset override switch currently matches only the stale ID. The generic factory path may still work, but that should be tested rather than assumed. - [Beacon runtime](../../beacon/Services/BeaconModelRuntime.swift#L478-L486); [canonical API](https://huggingface.co/api/models/mlx-community/SmolVLM2-500M-Video-Instruct-mlx)

### Gaps

- The audit did not download and hash every snapshot. HEAD byte totals come from Hugging Face's live `blobs=true` API and can change when `main` changes.
- Marketing parameter labels are not consistently exact parameter counts. For example, Llama """1B""" contains about 1.236B safetensor parameters; Beacon's `1.2` is defensible as a numeric count even though the display name follows Meta's 1B tier. - [Llama API](https://huggingface.co/api/models/mlx-community/Llama-3.2-1B-Instruct-4bit)

## What practical iPhone tiers should be used?

### Takeaway

Use download-size tiers as conservative catalog UX, not as a promise that a model will fit at every context length. Keep `<=1 GB` broadly available, make `1-2 GB` a Pro/recent-device tier, and treat `2-3 GB` as an advanced newest-Pro tier with shorter default context and an explicit memory warning.

### Cited Findings

| HEAD download tier | Catalog label | Practical target | Catalog policy |
|---|---|---|---|
| `<=1.0 GB` | **Standard** | iPhone 14 or newer | Eligible for onboarding/general recommendation after a device smoke test. Existing LFM2/LFM2.5, Gemma 1B, Qwen3 1.7B, Llama 1B, and corrected DeepSeek 1.5B sit at or near this boundary. - [Apple iPhone 14 specs](https://support.apple.com/en-us/111850); [catalog model APIs](https://huggingface.co/api/models/mlx-community/Qwen3-1.7B-4bit?blobs=true) |
| `>1.0-2.0 GB` | **Pro** | iPhone 15 Pro or newer; recent non-Pro devices only after measured validation | Not an onboarding default. Start with a moderate context window and warn that VLM image tensors add transient memory. SmolLM3, Granite, Qwen Coder, SmolVLM2, and Qwen2-VL belong here by corrected HEAD bytes. - [Apple iPhone 15 specs](https://support.apple.com/en-us/111831); [SmolLM3 API](https://huggingface.co/api/models/mlx-community/SmolLM3-3B-4bit?blobs=true); [Qwen2-VL API](https://huggingface.co/api/models/mlx-community/Qwen2-VL-2B-Instruct-4bit?blobs=true) |
| `>2.0-3.0 GB` | **Advanced** | Newest Pro-class iPhones; iPhone 15 Pro only after explicit peak-memory testing | Opt-in only, one general text model in this tier, shorter default context, and no guarantee during multitasking. Phi-3.5/Phi-4 and proposed Qwen3 4B Instruct are in this tier; a 2.779 GB VLM such as Ministral is materially riskier because vision adds transient memory. - [Phi-4 API](https://huggingface.co/api/models/mlx-community/Phi-4-mini-instruct-4bit?blobs=true); [Qwen3 Instruct API](https://huggingface.co/api/models/mlx-community/Qwen3-4B-Instruct-2507-4bit?blobs=true); [Ministral API](https://huggingface.co/api/models/mlx-community/Ministral-3-3B-Instruct-2512-4bit?blobs=true) |

- Apple defines `recommendedMaxWorkingSetSize` as the approximate GPU allocation that avoids harming runtime performance and recommends keeping total resource/heaps memory below it. The pinned runtime's wired-memory policies clamp against this device-specific value when available. - [Apple Metal documentation](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize); [pinned wired-memory policy](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXLMCommon/WiredMemoryPolicies.swift#L6-L21)
- Runtime memory is greater than download size because it includes weights plus workspace and active allocations such as KV cache; the pinned runtime's own budget-policy example explicitly models `weights + workspace + kvBytes`. - [Pinned wired-memory policy](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXLMCommon/WiredMemoryPolicies.swift#L116-L170)
- Apple notes that available device storage is lower than nominal capacity and varies with the OS and configuration, so Beacon should check free disk space independently of its inference-memory tier. - [Apple iPhone 14 storage note](https://support.apple.com/en-us/111850)

### Inferences

- Use corrected HEAD bytes for the tier boundary. This moves Qwen3 0.6B, Llama 3.2 1B, and DeepSeek R1 Distill 1.5B down by roughly half relative to their current catalog values, but device recommendations should change only after runtime tests because disk bytes and peak unified memory are different quantities. - [Qwen3 API](https://huggingface.co/api/models/mlx-community/Qwen3-0.6B-4bit?blobs=true); [Llama API](https://huggingface.co/api/models/mlx-community/Llama-3.2-1B-Instruct-4bit?blobs=true); [DeepSeek API](https://huggingface.co/api/models/mlx-community/DeepSeek-R1-Distill-Qwen-1.5B-4bit?blobs=true)
- A practical admission test should record cold-load peak memory, first-token latency, sustained tokens/second, thermal behavior, and peak memory at Beacon's maximum supported context on the oldest device in each tier. VLMs need a separate maximum-image-resolution test because preprocessing and vision activations are not represented by repository size. - [Apple working-set guidance](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize); [VLM processor path](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXVLM/VLMModelFactory.swift#L369-L407)
- Avoid labels such as """iPhone 14+""" based only on storage size. The final compatibility decision should use the live Metal recommended working set plus measured headroom for iOS and Beacon, and should refuse or warn when projected memory exceeds the budget. - [Apple working-set guidance](https://developer.apple.com/documentation/metal/mtldevice/recommendedmaxworkingsetsize); [runtime admission policy](https://github.com/ml-explore/mlx-swift-lm/blob/3.31.3/Libraries/MLXLMCommon/WiredMemoryPolicies.swift#L40-L59)

### Gaps

- Apple product specification pages do not publish RAM, and this research did not use unofficial RAM figures as a compatibility guarantee. The proposed device names are therefore conservative product tiers pending Beacon-specific measurements. - [Apple iPhone 14 specs](https://support.apple.com/en-us/111850); [Apple iPhone 15 specs](https://support.apple.com/en-us/111831)
- No physical-device benchmark results were available for the current 13 models, so exact context limits and minimum devices remain validation targets rather than established facts.
